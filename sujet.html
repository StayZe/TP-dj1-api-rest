Projet : une micro-API d'administration

Tu construis, TP après TP, une API REST qui pilote les conteneurs Docker de ta machine et tient l'inventaire à jour dans NetBox. Il n'y a pas de sujet séparé : le projet est le résultat des TP. C'est lui, dans son état à la fin de la dernière demi-journée, qui est noté.

Règles du jeu

  • Travail individuel, dans ton dépôt GitHub (public, ou privé avec le formateur invité).
  • L'historique de commits fait partie de ce qui est regardé : commite à chaque étape qui fonctionne, avec un message qui dit ce que tu as fait. Un dépôt à un seul commit sera examiné de près.
  • Aucun secret dans le dépôt, ni dans le code, ni dans l'historique. Le fichier .env est dans le .gitignore dès le premier commit. Seul .env.example (sans valeur) est versionné.
  • Le rendu est le dernier commit poussé à la fin de la troisième demi-journée. Les dépôts sont clonés à ce moment-là.

Assistants IA

Tu peux te servir d'un assistant IA comme d'un collègue : te faire expliquer une erreur, une notion, une documentation. Tu ne peux pas lui faire écrire le projet à ta place.

La règle est simple : tu dois pouvoir expliquer chaque ligne de ton dépôt. À la troisième demi-journée, n'importe quel étudiant peut être interrogé quelques minutes sur son propre code (« montre-moi où tu vérifies le label », « pourquoi 409 ici et pas 404 ? »). Un code que son auteur ne sait pas expliquer n'est pas considéré comme son travail, et la note du projet est revue en conséquence.

Ce qui est fourni

Fichier Rôle

Copie ces fichiers à la racine de ton dépôt.

Contraintes de forme

Elles ne sont pas négociables : la correction lance ton API sans toi.

  • Python 3, FastAPI, pydantic. Appels sortants avec requests.
  • Un Dockerfile à la racine du dépôt. L'API écoute sur le port 8000.
  • Un requirements.txt à jour.
  • Toute la configuration vient de variables d'environnement, rien n'est écrit en dur :
Variable Contenu
DOCKER_API_URL adresse de l'API Docker Engine
NETBOX_URL adresse de NetBox
NETBOX_TOKEN token NetBox
API_TOKEN_ADMIN token du rôle admin de ton API
API_TOKEN_READER token du rôle lecteur de ton API
WEBHOOK_SECRET secret partagé avec l'émetteur d'alertes

Le jour de la correction, ces six variables auront d'autres valeurs que les tiennes.

Le périmètre : le label adminapi.managed=true

Ton API ne voit et ne touche que les conteneurs qui portent le label adminapi.managed=true. Tout autre conteneur de la machine est, pour elle, inexistant : absent des listes, 404 si on le demande, jamais arrêté, jamais supprimé, jamais redémarré.

Les conteneurs que ton API crée reçoivent ce label.

Le contrat

Un conteneur est toujours représenté ainsi :

{
  "id": "4f1c…(identifiant Docker complet, 64 caractères)",
  "name": "web1",
  "image": "nginx:alpine",
  "state": "running"
}

state reprend l'état Docker : running, exited, created…

Lecture

Route Réponse
GET /health 200, {"status": "ok"}. Sans authentification.
GET /containers 200, la liste des conteneurs gérés.
GET /containers/{id} 200, le conteneur. 404 s'il est inconnu ou non géré.

Écriture

Route Réponse
POST /containers Corps {"name": "web1", "image": "nginx:alpine"}. Crée et démarre le conteneur. 201 et le conteneur.
422 si le corps est invalide. 409 si le nom est déjà pris.
POST /containers/{id}/stop 200 et le conteneur, state vaut exited. 409 s'il est déjà arrêté. 404 si inconnu.
POST /containers/{id}/start 200 et le conteneur, state vaut running. 409 s'il tourne déjà. 404 si inconnu.
DELETE /containers/{id} 204, sans corps. Le conteneur est supprimé, même s'il tourne. 404 si inconnu.

Validation des entrées de POST /containers :

  • name : une minuscule, puis 1 à 30 minuscules, chiffres ou tirets (^[a-z][a-z0-9-]{1,30}$) ;
  • image : allowlist de trois valeurs, nginx:alpine, redis:alpine, httpd:alpine.

Authentification

Header Authorization: Bearer <token>.

Qui appelle GET /containers… Routes d'écriture
Sans token, ou token inconnu 401 401
Token lecteur 200 403
Token admin 200 acceptée

/health, /metrics, /docs et /openapi.json restent ouverts.

Inventaire NetBox

Chaque conteneur géré par ton API a sa machine virtuelle dans NetBox, dans le cluster docker-local, sous le même nom :

Événement Dans NetBox
Création la machine virtuelle est créée, statut active
Arrêt son statut passe à offline
Démarrage son statut repasse à active
Suppression la machine virtuelle est supprimée

Webhook d'auto-remédiation

POST /webhooks/alerts, corps {"alert": "container_down", "container": "web1"}, header X-Webhook-Secret: <secret>.

Cas Réponse
Header absent ou secret faux 401, et rien n'est redémarré
Type d'alerte inconnu, corps invalide 422
Conteneur inconnu ou non géré 404
Alerte valide 202, le conteneur est redémarré et NetBox mis à jour
Alerte valide, mais le conteneur tourne déjà 202, rien à faire

Cette route n'utilise pas les tokens de l'API : l'émetteur d'alertes ne connaît que le secret.

Métriques

GET /metrics, sans authentification, au format texte Prometheus (Content-Type: text/plain) :

# HELP adminapi_containers Nombre de conteneurs gérés, par état.
# TYPE adminapi_containers gauge
adminapi_containers{state="running"} 2
adminapi_containers{state="exited"} 1
# HELP adminapi_remediations_total Redémarrages déclenchés par une alerte.
# TYPE adminapi_remediations_total counter
adminapi_remediations_total 3
  • adminapi_containers reflète l'état réel des conteneurs gérés au moment de l'appel ;
  • adminapi_remediations_total augmente de 1 à chaque redémarrage déclenché par le webhook (pas quand l'alerte est ignorée).

Documentation

/docs et /openapi.json sont générés par FastAPI. Chaque route porte un résumé (summary) rédigé, et ses codes d'erreur sont déclarés (401, 403, 404, 409 selon la route).

Le vérificateur

python verifier.py                 # tout
python verifier.py lecture         # un bloc
python verifier.py ecriture netbox # plusieurs

Il appelle ton API, puis va constater directement dans Docker et dans NetBox que ce que ton API prétend avoir fait est vrai. Il ne manipule que des conteneurs nommés verif-….

Bloc Construit au Points
lecture TP3 4
ecriture TP4 5
authentification TP5 3
netbox TP6 3
webhook TP7 2
metriques TP8 3

Dans chaque bloc, les points sont proportionnels au nombre de vérifications réussies.

La correction rejoue ces vérifications et en ajoute d'autres, que tu ne connais pas : autres noms, autres valeurs, entrées malveillantes. Une API qui respecte le contrat les passe sans y penser. Une API qui répond « ce que le vérificateur attend » sans rien faire de réel échoue.

Note finale

note finale = projet × 2/3 + quiz × 1/3, chaque composante sur 20.

Le quiz (20 questions, 30 minutes, sur feuille) a lieu à la dernière demi-journée. Il porte sur les concepts vus en cours, pas sur la syntaxe de FastAPI ou de requests.

Avant de rendre

  • ☐ python verifier.py : tous les blocs au vert.
  • ☐ docker build -t monapi . réussit depuis un clone neuf du dépôt.
  • ☐ git log --all --oneline -- .env n'affiche rien : le .env n'a jamais été commité.
  • ☐ .env.example est à jour, .env n'est pas versionné.
  • ☐ git status est propre et git push est fait.
